## 3. Role Enforcement and `service_role` (`createAdminClient`) Inventory

### 3.1 Three-layer role enforcement (`VIEWER`, `STAFF`, `ADMIN`)

1. **UI / Layout layer (presentation only):**
   - `ProtectedLayout` calls `requireAuthorizedUser()`.
   - `Navigation` shows **Upload center** only when `hasMinimumRole(user.role, "STAFF")` and **User access** only when `user.role === "ADMIN"`.
   - `/documents/upload/page.tsx` enforces `requireRole("STAFF")`; `/admin/users/page.tsx` enforces `requireRole("ADMIN")`.
   - On `/documents`, `DocumentPageActions` (Create folder / Manage folders) and `DocumentDeleteAction` (Delete) render only when `user.role === "ADMIN"`.
2. **Server API layer:**
   - Every Route Handler calls `getAuthorization()`, which verifies a valid Supabase Auth session, looks up `public.users` by lowercase email, and requires `status === 'ACTIVE'`.
   - Mutation routes additionally enforce `hasSameOrigin(request)` and role checks (`STAFF` for uploads and upload-destination listing; `ADMIN` for folder creation/settings, document deletion, user management, and Drive setup).
3. **Database RLS & `SECURITY DEFINER` RPC layer:**
   - `public.users`: `authenticated` can `SELECT` only their own row (`lower(email) = lower(auth.jwt() ->> 'email')`). All writes and full-table reads go through `service_role`-only RPCs (`admin_list_users`, `admin_create_user`, `admin_update_user`) that independently verify the actor is an `ACTIVE` `ADMIN`.
   - `public.documents`: `authenticated` has `SELECT` only, constrained by RLS policy `"Authorized active users can read active documents"` (`deletion_state = 'ACTIVE'` and caller is an `ACTIVE` row in `public.users`). No direct `INSERT`/`UPDATE`/`DELETE` is granted to `authenticated`.
   - `public.upload_attempts` and `public.document_folders`: RLS enabled with zero policies for `anon`/`authenticated` and all privileges revoked from browser roles; accessible only via `service_role`.

### 3.2 Complete inventory of `createAdminClient()` (`service_role`) call sites

Because `createAdminClient()` uses `SUPABASE_SERVICE_ROLE_KEY`, it **bypasses Row Level Security**. Every current call site is listed below:

| File | Line(s) | Operation Performed | Risk for `can_read_document` (Milestone 1+) |
|---|---|---|---|
| `src/app/api/documents/route.ts` | L26, L30 | `createUploadAttemptRepository` and `createFolderUploadAttemptRepository` for `POST /api/documents` | Low (writes/claims upload attempts; may return existing `document_id` on idempotent replay) |
| `src/app/api/documents/[id]/route.ts` | L24 | `createDeletionRepository` for `DELETE /api/documents/[id]` (calls deletion RPCs) | Low (`ADMIN`-only mutation) |
| `src/app/api/folders/upload-destinations/route.ts` | L10 | `createHierarchyRepository` to list enabled `document_folders` for `STAFF`/`ADMIN` | Medium once per-folder permissions exist in Milestone 2: must filter destinations by folder access |
| `src/app/api/folders/parents/route.ts` | L12 | `createHierarchyRepository` to list active parent folders for `ADMIN` | Low (`ADMIN`-only) |
| `src/app/api/folders/route.ts` | L17, L24 | `createFolderRepository` and `createHierarchyRepository` for `ADMIN` folder creation | Low (`ADMIN`-only) |
| `src/app/api/admin/folders/upload-settings/route.ts` | L10 | `createHierarchyRepository` for `ADMIN` destination settings | Low (`ADMIN`-only) |
| `src/app/api/admin/users/route.ts` | L9 | `createUserRepository` (`admin_list_users`, `admin_create_user`) | Low (`ADMIN`-only user table) |
| `src/app/api/admin/users/[id]/route.ts` | L9 | `createUserRepository` (`admin_update_user`) | Low (`ADMIN`-only user table) |

> **Audit finding:** Today, all document reads (`listDocuments`, `getDocumentById`, Open, Download) use `createClient()` (the user's SSR session client) and therefore go through `public.documents` RLS. However, `20260915000000_grant_service_role_documents_select.sql` grants `SELECT` on `public.documents` to `service_role`. Any future feature (search, exports, dashboard counts, notifications, relationships) must either use the user's RLS-bound client or explicitly filter via `can_read_document(actor_id, document_id)`.

## 4. Google Drive Integration and OAuth Status

1. **OAuth flow & scope (Confirmed):**
   - Configured in `src/lib/google/drive-oauth.ts` and `src/lib/google/drive-setup.ts`.
   - Uses a dedicated OAuth 2.0 client (`GOOGLE_DRIVE_CLIENT_ID`, `GOOGLE_DRIVE_CLIENT_SECRET`) and `GOOGLE_DRIVE_REFRESH_TOKEN` for the official storage account (`kiblawanwaterdistrict@gmail.com`).
   - Scope is strictly `https://www.googleapis.com/auth/drive.file` (`driveOAuthScope`). No service account or Shared Drive is used.
2. **How operations work:**
   - **Upload (`src/lib/google/drive.ts`):** Pre-generates a Drive file ID via `files.generateIds`, persists it in `upload_attempts` before media transfer, uploads bytes with `files.create` using that exact reserved ID (preventing duplicate Drive files on retry), and finalizes the `documents` row via RPC (`finalize_admin_upload` or `admin_finalize_folder_upload`).
   - **Open (`src/lib/documents/file-api.ts`):** Rejects non-`ACTIVE` deletion states, verifies the file exists and is not trashed in Drive (`getMetadata`), and returns a `307` redirect to the canonical Drive `webViewLink`.
   - **Download (`src/lib/documents/file-api.ts`):** Rejects non-`ACTIVE` deletion states, streams file bytes through the Next.js server (`files.get({ alt: "media" })`) with `Cache-Control: private, no-store` and `Content-Disposition: attachment`.
   - **Delete (`src/lib/google/drive-deletion.ts`):** Currently calls `files.update({ fileId, requestBody: { trashed: true } })` during `DELETE /api/documents/[id]` before calling `admin_finalize_document_deletion`.
3. **Google OAuth publishing status (Action Required):**
   - The OAuth consent screen publishing status (`Testing` vs `In production`) lives in the Google Cloud Console (`KWD Document Center` project) and cannot be read from repository files.
   - **Owner check required before Milestone 1:** Confirm in Google Cloud Console → *OAuth consent screen* whether the app is in **Testing** (which expires refresh tokens after 7 days) or **In production**.

## 10. Proposed Adjustments to Milestones 1–7

Based on the code findings above, the roadmap milestones hold up well, with four concrete adjustments:

1. **Milestone 1 (Trash, Restore, and Purge vs. existing Phase 7A RPCs):**
   - `admin_claim_document_deletion`, `admin_finalize_document_deletion`, and `admin_mark_document_delete_failed` already implement the exact lease/token state machine (`DELETE_PENDING` → `DELETE_FAILED` / finalized) needed for a Drive mutation.
   - **Adjustment:** In Milestone 1, repurpose the two-step claim/finalize Drive Trash flow for **Admin Purge** (`PURGE_PENDING` / `PURGE_FAILED` / `PURGED` or retaining the lease columns for Purge), and make **Delete** a single-transaction RPC (`admin_soft_delete_document`) that sets `deletion_state = 'DELETED'`, `deleted_at = now()`, `deleted_by = actor_id`, and writes the `audit_log` row without calling Google Drive.
2. **Milestone 2 (Reuse Phase 7D.3 columns instead of adding duplicates):**
   - `public.documents` **already has** `destination_folder_id` (FK to `public.document_folders`) and `source_relative_path`. Per-folder permissions in Milestone 2 should use `documents.destination_folder_id` (and `filing_year` / `document_type` / `filing_subcategory` for legacy rows where `destination_folder_id IS NULL`) rather than adding another folder foreign key.
   - `public.upload_attempts` **already computes and stores** `content_sha256 bytea` (32-byte SHA-256) for folder uploads (`src/lib/documents/folder-upload-validation.ts`). Milestone 2 duplicate detection should reuse that exact SHA-256 computation for single-file uploads as well and copy `content_sha256` into `public.documents` on finalization.
3. **Milestone 2 (Role mismatch to be aware of):**
   - Single-file upload (`finalize_admin_upload` in `20260909000000_add_admin_drive_uploads.sql`) checks `actor.role = 'ADMIN'`, whereas folder upload (`admin_claim_folder_upload_attempt` in `20261007000000_add_folder_upload_claim_finalize_rpc.sql`) and `POST /api/documents` (`src/lib/documents/file-api.ts`) allow `STAFF` and `ADMIN`. Confirm with KWD whether `STAFF` should also be allowed to use single-file upload (`finalize_admin_upload`), or if single-file and folder upload should share the same role check.
4. **Documentation sync in Milestone 1:**
   - Update `README.md`, `docs/06-data-model.md`, and `docs/12-development-roadmap.md` to reflect that Phases 1–5 and 7A–7E are already implemented, and document the existing `destination_folder_id`, `source_relative_path`, and `content_sha256` columns.
